# Sceneries are procedural three.js code, not loaded GLBs

Everything around the table (ground, buildings, sky, lights, the table itself, the chairs, the props on the table and the deck art) is a scenery built entirely in code: geometry from three.js primitives, textures drawn on canvases at start-up, lights and animated bits (flames, crows, moths, smoke, a dog breathing, a tube blinking) as plain objects updated per frame. There are two sceneries, the corner bar and the graveyard, and both implement one small interface (`scene/scenery/scenery.ts`): a group to add to the scene, four chairs, a deck art, fog, background, exposure, a walk radius, an update and a dispose. The scene swaps the whole thing when the room says another id.

The graveyard came from a standalone prototype that could export itself as a GLB, so loading a GLB per scenery was a real option: one binary per scenery, loaded through an asset pipeline, with the code only placing the camera and the cards. It lost for the same reasons the buddies did (ADR 0006), plus three of its own: the prototype's look depends on things a GLB export drops (canvas textures, lights, sprites, animated flames and crows), the project has no asset hosting or loading state and would need both, and every scenery-specific behaviour (where the candles sit so they miss the cards, the chair height the buddies sit on) is coupled to constants in the scene code, which a binary cannot read.

## Consequences

A scenery is a TypeScript module of a few hundred lines that runs headless: chair positions and heights, the walk radius and the prop-free card zones are asserted with `bun test`, which is how this project verifies without a browser. Textures are null in tests and materials tolerate that. The renderer settings moved to what the sceneries were designed for (ACES tone mapping, soft shadows, exponential fog, a far plane of 400 m), so the buddies and the cards now read under scenery light rather than flat light; a scenery that wants a different look changes its own lights and exposure, never the renderer. Adding a scenery means writing another builder against the interface and one id in the protocol list; there is no art toolchain to learn, and no way to drop in modelled scenery without first writing a loader and re-deriving the same constants.
